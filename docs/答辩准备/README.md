## 3 汇报主线和每组需要提供的内容

汇报顺序：系统目标与范围 → 系统整体结构 → 各模块的功能需求与逻辑分析 → 非功能需求 → 分工、总结与体会。

四组各准备两个页面的内容稿。这是准备内容的单位，最终 PPT 的页数、图和讲解时长由组长决定；不是让组员自行制作两页 PPT。报告仍按老师模板将功能描述与逻辑分析分别编排。

### 第一页 功能需求与典型流程

必须提供：

1. 页标题和一句话结论。
2. 3—5 条能直接放上幻灯片的短句，覆盖模块目的、参与者、两个用例各自的作用、关键权限或限制。
3. 选一个代表用例，说明前置条件、4—6 个主要步骤、关键异常分支和操作后的结果。另一用例也须在要点中介绍。
4. 一张现有主图的项目相对路径，以及图中要讲的具体节点或分支；其他图列作备用。
5. 约 150—250 字讲解稿，解释流程和规则，不简单重复上屏文字。

### 第二页 逻辑分析与建模

必须提供：

1. 页标题、一句话结论、3—5 条上屏短句。
2. 与典型用例对应的边界类、控制类、实体类及各自职责；类名与最新版图稿一致。
3. 1—2 个关键关联或多重性的业务含义，以及为什么这样划分职责。
4. 用 4—6 个关键步骤概括协作消息，引用现有图中的消息编号，说明异常时哪些后续操作不发生。
5. 一张主图的项目相对路径和讲图重点；另一分析图列为备用。
6. 约 150—250 字讲解稿。

每页优先一张主图，不把全部图塞进同一页。两页讲解应使用同一典型用例，便于从业务流程讲到对象协作。

### 同一文件末尾还要有

- 3 个带答案的问题：业务/权限、建模、异常流程各一个，每个答案 2—4 句。
- 实际贡献：分别列出前期和本轮本人完成的工作；合作组分人记录。不自行填写最终贡献百分比，比例由组长依据实际工作核定。
- 一项真实困难、处理办法与收获，供报告“总结和体会”使用。
- 待确认事项：若发现图文不一致，列出文件位置、问题和建议；无问题写“无”。不顺手改变范围或修改已有源图。

## 6 提交与验收

1. 同步最新 `main`，基于对应 Issue 创建个人任务分支（建议 `codex/issue-编号-模块英文简称`）。
2. 仅在本轮分配目录中新增/修改 `汇报材料.md`，并可删除自己的 `.gitkeep`；不要修改公共文件、原交付图文或他人的目录。
3. 发 PR 到 `main`，在描述中写 `Closes #对应Issue编号`，说明交付路径、实际参与人和待确认事项。
4. 组长审核后合并。需要修改时更新原文件，不另建版本副本。
5. 陈诺负责带翟宇豪完成上述流程；尚无协作权限时由陈诺统一提交。

验收清单：

- [ ] 两页均有标题、结论、上屏文字、配图位置和讲解稿
- [ ] 两个用例均有介绍，典型流程与分析模型对应
- [ ] 权限、分支、类名、关系、消息与最新图稿一致
- [ ] 3 个问题均有具体答案
- [ ] 实际贡献、困难、处理办法与收获齐全，合作组分人记录
- [ ] 没有多份版本、重复图片、本机绝对路径或未填写的空项
- [ ] 本人能解释所交内容；需要组长决定的内容明确列为待确认
